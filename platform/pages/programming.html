مُقدِّر تكلفة Big-O

Algorithmic Cost
عدد العمليات التقريبي 0
الزمن المتوقع — على 10⁸ ops/sec
التصنيف —
  • O(log n) دائماً مقبول. O(n²) يجب تبريره.
  • Hash map يحوّل O(n) إلى O(1) — استثمر في الذاكرة عند الحاجة.
  • في المقابلات: اذكر التعقيد قبل كتابة الكود.
  • Best/Average/Worst تختلف — تحدّث عن Worst افتراضياً.
⚠️ Big-O — مزالق فهم خاطئ 7
أكثر الأخطاء شيوعاً
  1. ✗ تركّز على الثوابت مع كبير الإدخالات — O(2n) و O(n) متطابقتان.
  2. ✗ تنسى أن O(log n) يفترض الفرز المسبق — sort نفسه O(n log n).
  3. ✗ تخلط بين best/average/worst case — Quicksort O(n²) في worst.
  4. ✗ تتجاهل space complexity — recursion عميقة تكسر stack حتى لو time جيد.
علامات تظهر عليك أنت
  • حلولك تفشل في leetcode hard → غالباً O(n²) خفي.
  • Code يبطئ مع large datasets فقط → غير مقاس على scale حقيقي.
  • قابل للقراءة لكن slow → optimization premature أو خاطئة.

تحقّق من فهمك

4 أسئلة · ~8 دقائق

  1. ما هو Big-O Notation ولماذا O(n²) "أسوأ" من O(n log n) عند n كبير؟

    ↓ اكشف الإجابة
    Big-O يصف كيف ينمو وقت الخوارزمية مع حجم المدخل. O(n²): لو n=1000 → مليون عملية. O(n log n): ~10,000 عملية. الفرق يظهر فقط مع بيانات كبيرة.

  2. رتّب: O(1), O(n), O(log n), O(n²), O(2ⁿ) من الأسرع للأبطأ.

    ↓ اكشف الإجابة
    O(1) < O(log n) < O(n) < O(n²) < O(2ⁿ). الأول ثابت والأخير ينفجر أسّياً.

  3. Loop داخل loop: for i in range(n): for j in range(n). ما الـ Big-O؟ ولو الداخلية range(i)؟

    ↓ اكشف الإجابة
    الأولى O(n²). الثانية: 1+2+...+n = n(n+1)/2 = O(n²) أيضاً (coefficient مختلف لكن نفس الـ class).

  4. متى O(n²) مقبول عملياً؟

    ↓ اكشف الإجابة
    لما n صغير ثابت (n<50). أو لما readability أهم من performance. مثال: sort لمصفوفة 10 عناصر — bubble sort أوضح من quicksort.

Debugging كمنهجية — لا كتجربة عشوائية
David J. Agans — Debugging: The 9 Indispensable Rules, 2002
مهارة حرجة
المنهجية العلمية في الـ Debugging
1) أعد إنتاج المشكلة بشكل موثوق. 2) اعزل المتغيرات: غيّر شيئًا واحدًا في كل مرة. 3) اقرأ رسالة الخطأ فعلاً — 70% من الحلول في الـ stack trace. 4) استخدم Binary Search: عطّل نصف الكود. المشكلة في النصف الذي ما زال يفشل. كرّر. 5) اشرح المشكلة لشخص آخر (Rubber Duck Debugging) — التفسير يُعيد ترتيب تفكيرك.
❌ أخطاء المبتدئين
تغيير أشياء عشوائية وتشغيل الكود "يمكن يزبط" — هذا ليس debugging بل قمار. لن تتعلم شيئًا حتى لو "نجح".
✅ عقلية الخبير
الخبير يسأل "لماذا يعمل؟" بنفس جدية "لماذا لا يعمل؟". إذا لا تفهم لماذا اختفى الـ bug — فهو لم يختفِ فعلاً.

🧊 Impostor Syndrome
70% من المبرمجين يشعرون أنهم "لا يستحقون" مناصبهم. هذا طبيعي بيولوجيًا. الخبراء يعرفون حدود معرفتهم — المبتدئون يعتقدون أنهم يعرفون كل شيء (Dunning-Kruger). إحساسك بالنقص دليل وعي لا ضعف.
🔄 Sunk Cost Fallacy
قضيت 3 أيام على حل معين. اكتشفت أن الحل خاطئ. هل تستمر "لأنك استثمرت وقتًا"؟ هذا Sunk Cost. الوقت المنقضي لا يُسترد — القرار الصحيح مبني على المستقبل لا الماضي. احذف الكود بثقة.
⏰ Planning Fallacy
البشر يُقلّلون تقديرات الوقت بنسبة 40-60%. قاعدة: ضاعف تقديرك الأولي. إذا قلت "يومين" — الحقيقة غالبًا 4 أيام. هذا ليس ضعفًا — هذا عيب بيولوجي في التقدير يمكن تصحيحه بالبيانات التاريخية.
🎯 Flow State

BLOCK D — تصميم الأنظمة (System Design)
ليس حفظ «المصطلحات» — بل تعلّم كيف تفكر أمام مشكلة بلا حل واحد. كل قرار معماري = trade-off.
🏛️ منهجية «4S» للتصميم
Scenarios → Services → Storage → Scale
1) Scenarios: ما الذي سيفعله المستخدم فعلاً؟ DAU، QPS، نسبة Reads/Writes، حجم الطلب الواحد.
2) Services: ما المكونات المنطقية؟ API Gateway، Auth، Business، Workers.
3) Storage: SQL أم NoSQL؟ العلاقات أم السرعة؟ Consistency أم Availability؟ (CAP).
4) Scale: أين يختنق النظام عند 10x؟ Cache، CDN، Sharding، Read-Replicas، Queue.
🧠 Active Recall — قبل أن تقرأ الإجابة
اضغط لاسترجاع المعلومة ذهنياً أولاً…
نظام مثل Twitter: 300M DAU، ~6K tweets/sec. السؤال: هل الـ bottleneck في الكتابة أم القراءة؟
الإجابة: القراءة. نسبة Read:Write تقارب 1000:1 — لذلك الحل = Fan-out on Write إلى Timeline Cache (Redis) لكل متابع. الـ storage المفضّل: Cassandra (write-heavy + eventually consistent) مع Redis للـ hot timelines.
⚖️ CAP Theorem — تختار اثنين فقط
C · Consistency: كل قارئ يرى آخر كتابة — دائماً.
A · Availability: كل طلب يحصل على رد — دائماً.
P · Partition Tolerance: النظام يعمل رغم انقطاع الشبكة.
في العالم الحقيقي P ليست خياراً — شبكات تتقطّع. فالاختيار الحقيقي بين CP (بنوك) وAP (سوشيال ميديا).
🔁 Idempotency — المفتاح الذي يُنقذ الإنتاج
Idempotent = تكرار الطلب لا يُغيّر النتيجة. POST /payments بدون idempotency key = كارثة عند retry. الحل: Client يُرسل Idempotency-Key: UUID والسيرفر يُخزّنه 24h. أي retry بنفس المفتاح = نفس النتيجة، بدون خصم مزدوج.
قاعدة: أي endpoint يُعدّل الحالة + يتعامل مع أموال = يجب أن يكون idempotent. لا استثناءات.
🌊 Backpressure — ما الذي يفعله النظام عند الغرق؟
الخوادم تتلقى طلبات أسرع مما تستطيع معالجتها. بدون backpressure = memory leak → crash → cascade failure.
الأدوات: Queue bounded (ترفض عند الامتلاء)، Circuit Breaker (يفتح الدائرة عند الفشل)، Rate Limiter (token bucket)، Load Shedding (إسقاط طلبات منخفضة الأولوية).

    Code Review Etiquette · ١٠ قواعد ⚖️

    الـ Code Review مهارة قيادية. سيّء = يقتل المعنويات. جيد = يرفع الفريق كله.

      "هذه الدالة يصعب اختبارها" — لا "أنت ماتختبر".

    2. اشرح "لماذا" — لا فقط "غيّر"

      اقترح بسبب: "لو فشل الـ API هنا، الـ UI يتجمّد. دعنا نُضيف timeout."

    3. "نحن" بدلاً من "أنت"

      "كيف نعالج حالة null هنا؟" يفتح حواراً بدل دفاع.

    4. امدح الجيد فعلاً

      "الفصل بين validation وservice نظيف جداً" — يبني ثقة.

    5. صنّف ملاحظاتك

    6. اقترح بدائل صغيرة بكود

      مقتطف 3 أسطر يوفّر 30 دقيقة جدال. اقتراح suggestion في GitHub أداة ممتازة.

    7. لا تُراجع وأنت متعب أو غاضب

      الإيقاع العاطفي يتسرّب. أجّل.

    8. راجع أولاً الـ goal ثم الـ implementation

      هل هذا يحلّ المشكلة الصحيحة أصلاً؟ — قبل تفاصيل التسمية.

    المهارات الناعمة للمبرمج 💬

    الفرق بين Junior وSenior كثيراً ما يكون هنا — لا في عدد اللغات.

    📐

    Estimation · قاعدة الـ 3x

    الـ Junior يُقدّر "هذا يومان" — يستغرق ٦ أيام (3x). السبب: غياب احتساب: review، testing، unknowns، meetings.

    • قسّم المهمة لـ < نصف يوم لكل قطعة قبل التقدير
    • أضف "buffer غموض" 20-30% للـ unknowns
    • اختم بـ "إذا اكتشفت X خلال أول 4 ساعات، سأُحدّث التقدير"

    ⚠️ متى لا تنطبق 3x: مهمة جربت مثلها قبل 3 مرات → التقدير يقترب من الواقع.

    ❓

    Asking Questions · سؤال جيد

    السؤال الجيد يوفّر وقت الجميع. اتّبع نموذج SSCCE: Short, Self-contained, Compilable, Example.

    • السياق: ماذا تحاول؟ (الهدف لا الكود)
    • المتوقع: ماذا تتوقع أن يحدث؟
    • الفعلي: ماذا حدث فعلاً؟ (مع رسالة الخطأ كاملة)
    • الذي جرّبته: ٣ محاولات على الأقل

    📌 قبل السؤال: ابحث ٢٠ دقيقة + اقرأ أول صفحة Google + اقرأ الـ docs الرسمية.

    📅

    Standup · ٣ جمل

    الـ daily standup ليس تقرير إنجاز — هو إشارة تنسيق.

    • أمس: "أنهيت endpoint الـ login + tests"
    • اليوم: "أبدأ refresh tokens"
    • عوائق: "أحتاج credentials للـ staging — @ali"

    ⚠️ تجنّب: قراءة كل ما فعلت، تفاصيل تقنية لا تهمّ غيرك، شكاوى عامة.

    🤷

    قُلها بثقة: "لا أعرف"

    أكثر مهارة سرّية للـ Senior. الـ Junior يُخفي الجهل → يعمل bugs خفية. الـ Senior يقول "لا أعرف، سأعرف خلال ساعة."

    • "لم أعمل على هذا قبلاً، لكن أتوقع X — هل تريد أن أتأكد؟"
    • "لست متأكدًا — أحتاج ٣٠ دقيقة فحص"
    • "لا أعرف، لكن @ahmed عمل مشروعًا مشابهاً قبل أشهر"

    📌 الثقة = الصراحة بحدود معرفتك، لا التظاهر بعكسها.

    👥

    Pair Programming · driver/navigator

    اثنان أمام نفس الكود: الـ driver يكتب، الـ navigator يفكر استراتيجياً. تبادلوا كل ٢٥ دقيقة.

    • navigator لا يقاطع driver في كل سطر — يُلاحظ نقاط بعدية
    • driver يفكر بصوت عالٍ — "الآن أتحقق من null"
    • تجنّب pairing > ٢ ساعات بدون استراحة — منهك ذهنياً

    📌 ممتاز للمهام الجديدة، التعلّم، debugging صعب. مكلف للأعمال الروتينية.

    📨

    كتابة رسالة Slack/Email احترافية

    القاعدة: BLUF = Bottom Line Up Front. الجملة الأولى تحمل الطلب أو الخلاصة.

    • سيّئ: "أمس كنت أعمل على... ثم... ثم... وأخيراً، ممكن صلاحية staging؟"
    • جيد: "أحتاج صلاحية staging لاختبار refresh tokens. السبب: نسخت credentials قديمة لكنها expired."

    📌 رسالتك تنافس ١٠٠ رسالة أخرى — اجعلها سهلة الردّ.
